## 1. Summary

AcsTool already captures the **application layer**: every CWMP HTTP exchange that passes through the proxy or the simulator is
stored as an `ExchangeRecord` (request/response `HttpMessageCapture`, `MessageSummary`, `UpstreamError`, `ExchangeTimings`)
inside a `SessionSnapshot` in `InMemorySessionStore`. That answers *"what did the CPE and the ACS say?"*.

Packet Trace adds the **wire layer**: TCP/IP frames captured from selected NICs (and loopback) with libpcap/Npcap through
**SharpPcap**, decoded with **PacketDotNet**, shown in a Wireshark-like three-pane view, linked to the sessions/exchanges the app
already captured, and exportable to PCAPNG for Wireshark. It answers *"what actually happened on the network?"*: SYN without
SYN-ACK, RSTs, retransmissions, zero windows, a CPE that sends half a request, an ACS that closes before responding, TLS alerts on
an HTTPS leg, DNS that never answers.

**Primary story (r2):** *an Inform arrives → the Proxy tab shows the app-layer session **and** its packets.* The user ticks
**Capture packets** on the Proxy toolbar once; from then on, selecting a session or an exchange in the Proxy feed/detail shows a
**Packets** tab next to Summary / Headers / Raw with exactly the frames of that exchange (or the whole session) on both legs —
CPE ↔ Proxy and Proxy ↔ ACS — with protocol tree and hex. No context switch to another tab is needed to follow the Inform. The
standalone **Packet Trace** tab remains for capture-console tasks: NIC/BPF control, unconstrained live browsing, connections that
never became a session, and offline `.pcap`/`.pcapng` files.

The packet layer **never re-implements** the HTTP capture: it does not write to `ISessionSink`, and for CWMP bodies rebuilt from
the wire it reuses the existing `ICwmpParser` and `IMessageSummarizer`.

## 2. Goals and non-goals

### Goals (mapped to Fariborz's requirements R1–R9)

| # | Goal | Phase |
|---|---|---|
| R1 | Live capture on one or more selected NICs **plus loopback**; Npcap detection and guidance on Windows; clear privilege errors. | MVP (PT1) |
| R2 | BPF capture filter, generated by default from the proxy settings (listen port 7547, HTTPS port, upstream host/port); editable; "limit to session" quick filter. | MVP |
| R3 | **(r2) Packets in the Proxy tab:** a **Packets** tab in the session detail area (next to Summary/Headers/Raw, whose content is unchanged) showing the selected exchange's or session's frames on both legs, with compact list / protocol tree / hex; a **Capture packets** toggle on the Proxy toolbar. Plus a secondary **Packet Trace** tab (full three-pane list/tree/hex) for unconstrained browsing, capture settings, and offline files. | MVP (both; the Proxy integration is the critical path) |
| R4 | Correlate packets ↔ `SessionSnapshot`/`ExchangeRecord` by 4-tuple (+ Kestrel connection id, time window), **down to the exchange** so the Proxy detail can show "this Inform's packets". | MVP (tuple + request-order segmentation, §6.4) → PT2 (exact HTTP-message match) |
| R5 | Follow TCP stream; rebuild HTTP/1.1 and CWMP from reassembled payload. | PT2 |
| R6 | Export selected packets / stream / session / all to PCAPNG (PCAP optional) in the exports folder; "Open in Wireshark". | MVP |
| R7 | Live capture **and** offline `.pcap`/`.pcapng` analysis in the same view. | MVP (open file) → PT3 (wire sessions) |
| R8 | Bounded memory: packet count + byte budget, snap length, bounded queues, visible drop counters. | MVP |
| R9 | Clean integration with Kestrel proxy and `InMemorySessionStore`; no duplication of `HttpMessageCapture` logic. | MVP |

### Non-goals

- Decrypting TLS on Windows (not possible with SChannel, see §11.1). The app-layer capture already has the plaintext of the HTTPS legs.
- Packet injection, ARP/MITM, promiscuous sniffing of other hosts' traffic as a goal (promiscuous mode is a per-device option, default off).
- Replacing Wireshark: dissection covers Ethernet/Null/SLL/SLL2/Raw, IPv4/IPv6, TCP/UDP/ICMP, DNS (summary only), TLS record headers, HTTP/1.1, CWMP. Everything else is shown as raw bytes; "Open in Wireshark" is the escape hatch.
- HTTP/2, QUIC, IP fragment reassembly (shown as fragments; later if ever needed).
- Importing wire-rebuilt sessions into `InMemorySessionStore` (D12).
- Bundling or silently installing Npcap (license, D3).

### Gaps found in the current code (contradictions with the brief's assumptions)

- **G1 — no transport identity on exchanges.** `ExchangeRecord` has no connection id or endpoints. `SessionSnapshot.ClientEndpoint`
  is the endpoint of the *first* request only (set in `CpeSessionTracker` → `SessionStart`); a CPE that opens a new TCP connection
  mid-session (common after a 401 or with `Connection: close`) gets a different source port that is recorded nowhere.
- **G2 — Kestrel local endpoint not captured.** `ProxyRequestHandler.Snapshot` takes `RemoteIpAddress/RemotePort/Id` but not
  `LocalIpAddress/LocalPort`, so with `BindAddress = 0.0.0.0` on a multi-homed PC we don't know which NIC the CPE used.
- **G3 — upstream local port not captured.** `PhaseTracker` keeps only `RemoteEndPoint`. Without the local ephemeral port the
  proxy→ACS packets cannot be tied to a session (all sessions talk to the same ACS ip:port).
- **G4 — `ISessionStore.Changes` is single-reader** (`SingleReader = true`, consumed by `SessionFeedPump`). The packet correlator
  must not read it; it polls snapshots instead (§6.3).
- **G5 — default upstream is loopback** (`ProxySettings.UpstreamUrl = "http://localhost:7557"`). The proxy→ACS leg is then only
  visible on the loopback adapter (Npcap "Adapter for loopback traffic capture" / Linux `lo`), so multi-device capture is MVP, not a nice-to-have.
- **G6 — two clocks.** `ExchangeTimings.Started` comes from `TimeProvider.GetUtcNow()`; packet timestamps come from the driver.
  They agree to within a few ms on one PC but are not the same clock; correlation uses them only as a tie-breaker window.
- **G7 — milestone numbering.** `PLAN.md` uses M5 = Auth/cookies, M6 = TLS; `M5_TASKS.md` renumbered TLS to M5. To avoid a third
  numbering, this feature uses its own prefix **PT** (PT0–PT4) (D1).

### 5.2 No conditional compilation; runtime gating (D2)

PacketCapture is a plain `net10.0` library: SharpPcap and PacketDotNet are managed assemblies and load fine on Linux and Windows.
The only platform dependency is the **native** pcap library, loaded lazily by SharpPcap on the first device enumeration. So:

- No `#if WINDOWS`, no separate `-windows` TFM, no stub project. Everything compiles and unit-tests on Linux CI.
- `ICaptureBackend.Probe()` (new) returns `CaptureBackendStatus { Available, NotInstalled, AccessDenied, Error }` + version string
  + message. `SharpPcapBackend.Probe()` wraps `CaptureDeviceList.Instance`/`Pcap.Version` and maps `DllNotFoundException` →
  `NotInstalled`, `PcapException`/`UnauthorizedAccessException` with "access"/"permission" → `AccessDenied`.
- The Packet Trace tab is always present. When the backend is not available, the live-capture toolbar is disabled with an inline
  explanation and an **Install Npcap…** link; **Open file…** still works (offline analysis needs no native library — §9).
- Tests use `FakeCaptureBackend` (in `AcsTool.Testing`), which plays scripted frames through the same `ICaptureBackend` contract.

### 5.3 Threading model

```
 NIC A (Npcap)        NIC B / Loopback          Kestrel (thread pool)          UI thread (WPF Dispatcher)
 ┌──────────────┐    ┌──────────────┐           ┌───────────────────┐          ┌─────────────────────────┐

```

Rules (numbered to extend PLAN §3.8):

- **PT-1 Capture callback does O(copy) work only.** SharpPcap raises `OnPacketArrival` on its own capture thread (one per
  device). The handler copies the bytes (≤ snap length) into an array rented from `ArrayPool<byte>.Shared` (or an exact-size copy;
  see PT1.7), stamps the interface id and timestamp, and `TryWrite`s to the ingest channel. No decoding, logging, locking, or
  allocation of `Packet` objects on that thread. A slow callback makes the driver drop packets.
- **PT-2 Bounded ingest queue, DropWrite.** `Channel.CreateBounded<RawFrame>(20_000, FullMode = DropWrite, SingleReader = true,
  SingleWriter = false)` with the `itemDropped` callback incrementing `AppDropped`. DropWrite (drop the *newest*) rather than
  DropOldest because the ingest thread has already started reassembling the older frames; dropping newest keeps every stream
  contiguous up to the overload point, and the gap is visible as a marker row (`⚠ 1,234 frames dropped (app queue full)`).
- **PT-3 One dedicated ingest thread** (`Task.Factory.StartNew(…, TaskCreationOptions.LongRunning)`), not the thread pool, so a
  capture burst can never starve Kestrel's request tasks or the store's callers. It merges all devices (frames are numbered in
  arrival order; per-device timestamps are kept, the list can sort by time).
- **PT-4 Decode lazily.** The ingest thread computes only `FrameSummary` (≈ 100 bytes: time, interface, src/dst, protocol, length,
  TCP flags/seq/ack/payload length, stream id, short info). The full protocol tree and hex view are built **on demand** for the
  selected frame on a background task and cached for the last N selections.
- **PT-5 PacketStore is append-only with a budget** (§7). Readers (pump, correlator, export) take a consistent range by frame
  number; eviction moves a "first available" cursor. Readers holding a frame reference keep it valid (frames are immutable).
- **PT-6 The UI never sees one notification per packet.** `PacketFeedPump` (new, modelled on `SessionFeedPump`) wakes every 100 ms
  (250 ms when > 2,000 new frames), takes the new frame range, builds `PacketRowViewModel`s **off the UI thread**, and does one
  `IUiDispatcher.InvokeAsync` per batch (≤ 10/s). In "auto-scroll" mode only the visible tail matters; the list is virtualized
  (`VirtualizingStackPanel`, `VirtualizationMode=Recycling`, fixed row height).
- **PT-7 Correlation is pull-based** (G4). `SessionCorrelator` runs every 1 s on the thread pool: it calls `ISessionStore.GetAll()`
  only when `CaptureStats` changed, rebuilds an `EndpointIndex` incrementally for sessions not yet indexed, and tags the
  `TcpConversation`s that are still unlinked. It never reads `ISessionStore.Changes`.
- **PT-8 Start/stop and shutdown.** `PacketCaptureService.StopAsync` stops every device (`StopCapture` joins SharpPcap's thread),
  completes the channel, awaits the ingest loop (2 s cap, then logs 7090). `MainViewModel.ShutdownAsync` stops packet capture
  **first** (before the proxy) so that the proxy's final FIN/RST packets are not mis-processed during disposal, then the existing order.
- **PT-10 (r2) Proxy detail Packets tab refresh.** `ExchangePacketsViewModel` is only active while its tab is visible and a
  session is selected. It subscribes to `IPacketLookup.LinksChanged` filtered by its session id and to the store's frame cursor,
  recomputes its frame set off the UI thread, and applies at most **4 updates/s** (coalesced). An Inform that is still in flight
  therefore fills in live (SYN → request segments → upstream SYN … → response) without touching the session feed's pump.
- **PT-9 Async rules from PLAN §3.8 apply** (no `.Result`/`.Wait()`; library code `ConfigureAwait(false)`), except the capture
  callback which is synchronous by contract.

Why this cannot starve the UI: the UI thread does (a) one batched append per ≤ 100 ms, bounded by `MaxListRowsLive` and virtualized
rendering, and (b) on-demand tree/hex for one frame computed off-thread. Why it cannot starve Kestrel: capture threads are SharpPcap's
own threads, ingest is a dedicated thread, and the only shared lock with the proxy is the store's `_gate`, taken by `GetAll()` at
most once per second.

### 5.4 Privileges and Npcap (Windows) — D3, D4

| Topic | Design |
|---|---|
| Install | The user installs Npcap from <https://npcap.com> (not bundled: the free edition does not allow redistribution and silent install is OEM-only). Recommended installer options: defaults (**"Restrict Npcap driver's access to Administrators only" unchecked**, "WinPcap API-compatible mode" either way). Loopback capture is built in on current Npcap (the "Adapter for loopback traffic capture", device `\Device\NPF_Loopback`); the legacy `/loopback_support` option is **not** needed. |
| Detection | `Probe()` when capture is first needed — proxy start with **Capture packets** on, or opening the Packet Trace tab (r2) — never at app start, so `--smoke-exit` and startup are unaffected. `NotInstalled` → banner "Npcap is not installed. Live capture is disabled; you can still open .pcap/.pcapng files. [Get Npcap]". Version shown in the tab footer (`Pcap.Version`). |
| Elevation | App stays **`asInvoker`** (`app.manifest` unchanged). With default Npcap, normal users can capture. If Npcap was installed "admin only", opening a device triggers Npcap's `NpcapHelper.exe` UAC prompt per process; if declined, `Open` fails → `AccessDenied` banner: "Npcap is restricted to administrators. Accept the UAC prompt, run AcsTool as administrator, or reinstall Npcap without 'admin only'." We never self-elevate the whole app (Kestrel binding, settings paths and DPAPI scope would change). |

### 6.3 Correlation strategy

Correlation works at **conversation** granularity (one TCP connection), then refines to **exchange** granularity.

1. **Index** (`EndpointIndex`, rebuilt incrementally by `SessionCorrelator` from `GetAll()`):
   `TcpStreamKey(DownstreamRemote, DownstreamLocal)` → (SessionId, Leg = CpeToProxy, [seq…]) and
   `TcpStreamKey(UpstreamLocal, UpstreamRemote)` → (SessionId, Leg = ProxyToAcs or SimulatorToAcs, [seq…]).
   For `DownstreamLocal = 0.0.0.0`-style wildcards (shouldn't happen — Kestrel reports the concrete local address) fall back to
   (remote ip:port, local port).
2. **Conversation match** — exact 4-tuple match ⇒ `Confidence = Exact`. Port reuse is disambiguated by time: the conversation's
   `[FirstTicks, LastTicks]` must overlap `[Started − 2 s, (Ended ?? now) + 2 s]` of the session (tolerance for G6).
3. **Exchange match (PT2)** — once HTTP messages are rebuilt (§10), the n-th request on a downstream conversation is matched to the
   exchange whose `Endpoints.DownstreamConnectionId` equals the conversation's id **and** whose method/path/`Content-Length` match;
   ties broken by `ExchangeTimings.Started` nearest to the request's first frame. Body check: the first
   `min(Request.Body.Length, 4 KiB)` bytes must be equal (`HttpMessageCapture.Body` may be truncated — compare the prefix only).
   Upstream leg: same, matching against what `UpstreamForwarder` sent (method + rewritten URL path).
4. **No match** — conversations on the CWMP ports that match nothing are shown as "unlinked" (often the interesting case:
   a CPE whose SYN never got through, or a connection Kestrel reset before HTTP parsing). Probable matches (same CPE IP, time
   overlap, no tuple) are shown as `Probable` with a dotted icon, never as exact.
5. **Simulator through the proxy on one PC** — the simulator's upstream conversation *is* the proxy's downstream conversation on
   loopback; the same conversation then links to **two** sessions (Simulator source and Proxy source). `ConversationLink` is a
   list in that case; the UI shows both.
6. **Offline files** — no sessions exist; conversations are unlinked unless the capture is opened while the matching sessions are
   still in the store (works for "export, re-open" round trips). PT3 adds display-only "wire sessions" (§10.3).

What the user sees: a **Session** column (short device key / `sim:` label + seq numbers) in the packet list, the session's outcome
icon, a "Packets for this session" filter, and in the tree pane an "AcsTool" node: `Session 3f2a… · exchange #2 (GPVResponse) ·
leg CPE→Proxy · match: exact`.

### 6.4 (r2) Exchange-scope packets for the Proxy detail — MVP without reassembly

The Proxy detail needs "the packets of exchange #n" in the MVP, before PT2's reassembler exists. MVP rule, per leg:

1. Take the conversation(s) linked to the session for that leg (§6.3 items 1–2). The downstream conversation is the one whose
   4-tuple equals the exchange's `Endpoints.DownstreamRemote/Local`; the upstream one matches `UpstreamLocal/Remote`.
2. **Request-order segmentation:** within a conversation, a client→server segment whose TCP payload *starts* with an HTTP method
   token (`POST `, `GET `, …) opens a new request slot. Slot *k* on the downstream conversation ↔ the *k*-th exchange of the
   session carrying that `DownstreamConnectionId` (ordered by `Seq`); same on the upstream conversation by `UpstreamConnectionSerial`.
   This holds because exchanges of one `ProxySession` are serialised by `ProxySession.Gate` and HTTP/1.1 on one connection is
   in order. A slot spans from its first segment to the frame before the next slot (or FIN/RST).
3. **Connection frames** (SYN/SYN-ACK/ACK and FIN/RST) are attached to the first/last exchange that used the connection and
   shown greyed in neighbouring exchanges' views ("connection setup, shared").
4. **Fallback** when (2) fails (TLS leg — payload encrypted, CPE pipelining, a slot count mismatch): time window
   `[Started − 50 ms, Started + Total + 50 ms]` on the linked conversations, labelled "matched by time".
5. Every exchange view states its basis: `exact (connection + request order)`, `by time`, or `no packets (capture off / not
   captured / evicted)`, so the user never mistakes absence of data for absence of traffic.

PT2 replaces (2) by the exact HTTP-message match of §6.3 item 3 and adds the wire-vs-app diff.

## 7. Memory budget and limits (R8) — D8

New settings section (persisted in `settings.json`, optional; `AppSettings.Normalize()` fills defaults, `SchemaVersion` stays 1):

```csharp
public sealed record PacketCaptureSettings(
    int SnapLength = 65_535,                 // bytes per frame kept (full CWMP frames; Npcap/libpcap max 262144)
    int MaxFrames = 200_000,                 // ring capacity (live)
    long FrameBudgetBytes = 134_217_728,     // 128 MiB of frame data (+~20% object overhead; separate from Capture.CaptureBudgetBytes)
    int IngestQueueCapacity = 20_000,
    int KernelBufferBytes = 16_777_216,      // per-device pcap buffer (Npcap default is 1 MiB; raise to absorb bursts)
    bool Promiscuous = false,
    string? CaptureFilterOverride = null,    // null ⇒ generated (§8.1)
    bool IncludeDnsAndIcmp = true,
    IReadOnlyList<string>? SelectedDevices = null, // device names; null ⇒ auto (D10)
    WhenFull WhenFull = WhenFull.EvictOldest, // or StopCapture
    long ReassemblyBudgetBytes = 33_554_432, // PT2: 32 MiB for stream reassembly buffers
    bool MaskCredentialsOnExport = true,
    bool CaptureWithProxy = true,            // r2 / D15: Proxy-toolbar toggle; capture starts/stops with the proxy (needs Npcap)
    double LinkedShare = 0.75,               // r2 / D8: max share of the budget for frames linked to live sessions
    string? WiresharkPath = null);
```

- **(r2) Linked-first retention.** Because the primary view is "packets of a session in the Proxy feed", frames linked to a
  session still in `InMemorySessionStore` are kept preferentially: `PacketStore` evicts, oldest first, (1) unlinked frames,
  (2) frames whose session has been evicted from the store, and only then (3) linked frames of live sessions. Linked frames may
  use at most 75 % of the budget (`LinkedShare = 0.75`) so the capture console never goes blind. Implementation: two FIFO
  segments (linked / other) rather than per-frame scanning.
- `PacketStore` evicts while `count > MaxFrames || bytes > FrameBudgetBytes` (live) and shows "first frame #N
  (older frames evicted)". Offline files obey the same budget: opening a bigger file loads the first `MaxFrames`/budget and shows
  "file truncated at frame N — open in Wireshark for the rest".
- Evicting a frame never invalidates `TcpConversation` metadata (counters stay; the "Follow stream" view marks the evicted prefix).
- Drop accounting is shown in the tab footer and the main status bar: `pkts 123,456 · 87 MB/128 MB · dropped: kernel 0 · if 0 · app 0`.
  Kernel/interface counts come from `ICaptureSession.ReadCounters()` (SharpPcap `Statistics`) polled every 1 s.
- Memory worst case ≈ `FrameBudgetBytes` + 200k × ~150 B summaries ≈ 160 MiB + ≤ 32 MiB reassembly. Together with the
  existing 256 MiB session budget the app stays well under 1 GiB.

| Source | Read path | Native lib needed |
|---|---|---|
| Live | `SharpPcapBackend` → `LibPcapLiveDevice` (one `ICaptureSession` per selected device) | Yes (Npcap/libpcap) |

## 10. Stream follow and HTTP/CWMP rebuild (R5)

### 10.1 MVP (PT1) — per-segment only

- `TcpStreamTracker` assigns stream ids (Wireshark-like `tcp.stream` order), tracks SYN/FIN/RST, client/server roles, byte counts,
  simple analysis flags (retransmission = seq already seen with payload; zero window; RST; "SYN no answer" after 3 s).
- Protocol tree for a frame shows Ethernet/Null/SLL → IP → TCP (all header fields, flags, options) → payload. If the payload
  starts with an HTTP request/status line, the tree shows a **"HTTP (segment)"** node with the first line and the headers that
  are complete within this segment. TLS record headers (content type, version, length; handshake type; ClientHello SNI) are
  shown for port-443/7443 or when the first byte is 0x14–0x17.
- **Conversation list** pop-up (like Wireshark's Statistics → Conversations): per stream: endpoints, leg, linked session, state,
  frames, bytes, duration, problems. Selecting one filters the list to `tcp.stream == N`.

### 10.2 PT2 — reassembly and HTTP/CWMP rebuild

- `TcpReassembler` per stream and direction: orders segments by seq (32-bit wrap aware), drops exact retransmissions, keeps
  overlapping data first-wins, records gaps (missing bytes from loss, snaplen truncation, or eviction) as explicit gap markers;
  bounded by `ReassemblyBudgetBytes` (oldest closed streams are released first; a stream over budget keeps headers + first/last
  64 KiB and marks the middle as "not kept").
- `HttpWireExtractor` consumes the reassembled byte stream: HTTP/1.1 request/response framing with `Content-Length`,
  `Transfer-Encoding: chunked` (de-chunk), keep-alive (multiple messages per connection), `Expect: 100-continue`/`100 Continue`,
  `Connection: close` / read-to-close bodies, 204/304/1xx without body. Output: `WireHttpMessage(StreamId, Direction,
  FirstFrame, LastFrame, StartLine, Headers, Body (bounded by Capture.MaxCapturedBodyBytes), Complete, Problems)`.
  **This is not a second `HttpMessageCapture` pipeline**: nothing is written to the session store; it exists to show what was on the
  wire and to diff against the app's capture.
- CWMP: the body goes through the existing `ICwmpParser.Parse(span, contentType)` + `IMessageSummarizer.Summarize(...)` so the
  packet tree shows the same summary fields as the Summary tab (e.g. `Inform · BOOT, PERIODIC · OUI-PC-SERIAL`).
- **Follow TCP Stream** window: both directions interleaved, client red / server blue, ASCII / hex / "HTTP messages" modes, gap
  markers, "Save as raw" (`.bin`) and "Export this stream (.pcapng)".
- **Wire vs app diff** (the payoff of R4 + R5): for a linked exchange, the tree's "AcsTool" node shows `on wire: 1,842 B request,
  204 response · app: same` or flags differences: request seen on CPE leg but **no SYN on ACS leg** ("never left the PC"); ACS
  leg RST before response; response bytes on wire but app recorded timeout; header differences introduced by `HeaderRewriter`
  (expected, labelled "rewritten by proxy").

### 10.3 PT3 / later

- "Wire sessions" for offline files: group rebuilt CWMP messages into sessions with the same rules as the proxy
  (`CpeSessionTracker.EvaluateEnd` logic is *referenced* for documentation but not shared — it depends on proxy state; the wire
  grouping is simpler: by CPE IP + cookie + Inform boundary). Display-only (D12).
- IP fragment reassembly, TCP stream graphs, RTT/throughput stats: later only if asked.

## 11. Risks and limitations

### 11.1 TLS on the wire (HTTPS upstream, M5 HTTPS listener)

- Proxy→ACS over HTTPS (production) and CPE→proxy over HTTPS (M5 port 7443) are encrypted on the wire. Packet Trace shows TCP and
  TLS **record-layer** facts only: handshake messages (ClientHello SNI/versions/ALPN, ServerHello version, alerts with
  description), record sizes, who closed and how. That is still decisive for "does it die on the network?" (e.g. ACS sends
  `handshake_failure` alert vs. TCP RST vs. silence).
- **No decryption on Windows.** .NET's `SSLKEYLOGFILE` support (since .NET 9, opt-in via `System.Net.EnableSslKeyLogging`) works
  for `SslStream` only where .NET uses OpenSSL — i.e. Linux, not Windows/SChannel. So we do not offer key logging in the Windows app.
  The plaintext for those legs is the app-layer capture (Summary/Headers/Raw), linked from the packets (§6.3). A Linux-only
  key-log option is listed as PT4 "maybe".
- Pinned/CustomCa TLS errors: correlate the TLS alert frame with `SessionSnapshot.Tls` / `UpstreamError(Kind = Tls)` so the
  user sees "certificate rejected by AcsTool (client side)" vs "alert from the ACS".

### 11.2 Loopback capture

- Default upstream `localhost:7557` and simulator→proxy traffic are loopback-only (G5). Npcap's loopback adapter has link type
  **DLT_NULL** (4-byte family header) and no MACs; Linux `lo` is Ethernet with zero MACs (or SLL/SLL2 with the "any" device).
  The decoder handles all four link types; tests cover each.
- Loopback traffic on Windows is captured via WFP and appears **once** per direction; packets have no offload effects but may
  show huge segments (64 KiB). The NPF loopback adapter needs the BFE service (troubleshooting entry).
- A CPE talking to the PC's own LAN IP from the PC itself (simulator → `http://192.168.1.10:7547`) is also loopback on Windows,
  not the LAN NIC — the device picker explains this ("traffic to this PC's own IPs appears on the Loopback adapter").

### 11.3 Admin rights / Npcap install

- Npcap missing, admin-only mode, UAC declined, driver broken after a Windows update, maximum number of filter drivers reached
  (`0x8004a029`) — each maps to a specific banner text and a troubleshooting section (PT1.15). No silent install (OEM only).
- AcsTool CI (Windows runner) has **no Npcap**; live capture is never exercised in CI → manual checklist (TASKS §TesterBot).

### 11.4 CPU / memory / proxy latency

- Capture cost at the CWMP rates this tool sees (tens of packets/s; hundreds with 100 simulated CPEs) is negligible. The risk is
  a user removing the BPF filter on a busy NIC (10k+ pps): mitigations are the bounded queue with DropWrite, lazy decoding,
  kernel buffer 16 MiB, budgeted ring, visible drop counters, and a "No filter on a busy NIC — expect drops" warning when the
  filter is empty.
- Acceptance target (NFR-PT-2): at 5,000 pps synthetic load for 60 s the app drops < 0.1 % in the app queue, the UI stays
  responsive (< 100 ms input latency), and proxy p95 added latency stays < 5 ms with capture on vs off.

### 11.5 Other

| Risk | Mitigation |
|---|---|

## 12. Export and "Open in Wireshark" (R6) — D6, D7

### 12.1 Scope and format

- Scopes: **exchange** (r2: from the Proxy detail Packets tab — the exchange's frames on both legs) · **selected frames** · **displayed (filtered) frames** · **TCP stream** · **session** (all conversations linked to a
  session: CPE leg + ACS leg + their DNS/ICMP by time window) · **all frames**.
- Default format **PCAPNG** (D6): one Section Header Block (shb_userappl = `AcsTool <version>`, shb_os), one Interface
  Description Block per capture device (`if_name`, `if_description` = friendly name, `if_tsresol` = 7 (100 ns), `if_filter` =
  the BPF string, link type), Enhanced Packet Blocks with `opt_comment` = `AcsTool session=<guid> exch=<seq> leg=CpeToProxy`
  for linked frames (Wireshark shows these as packet comments, filterable with `frame.comment contains "session="`).
- **PCAP** (legacy) available in the dialog; it cannot hold several link types, so a mixed (Ethernet + loopback Null) selection
  exports one file per link type (`…-eth.pcap`, `…-loopback.pcap`) with a notice.
- File location: `IAppPaths.DefaultExportDir` (`Documents\AcsTool\exports`) + `packets\` subfolder, name
  `acstool-<yyyyMMdd-HHmmss>-<scope>[-<device-key>].pcapng`; created on first export. "Save as…" via existing `IFileDialogService.SaveFile`.
- Writing runs off the UI thread with progress (frames written) and cancellation; atomic write (temp file + rename, same pattern as
  `AtomicFile` in Core/Util).

### 12.2 Credential masking (AuthRedactor interaction) — D7

Plaintext CPE/ACS HTTP carries `Authorization: Basic …`/`Digest …`. PLAN NFR-08 / Q11 require exports to redact it by default.
In a packet capture we can't change lengths without breaking TCP sequence numbers, so masking is **same-length**:

- `CredentialMasker` finds `Authorization:`/`Proxy-Authorization:` header values (using `AuthRedactor.IsSensitive` for the name
  match) and overwrites the **value bytes after the scheme** with `*` (keeps `Basic `/`Digest username="…" ` readable for
  Digest: the `username` parameter is kept, other parameters masked — mirrors `AuthRedactor.Redact`'s policy), then recomputes
  the TCP checksum (and leaves IP length untouched). The export adds a comment `credentials masked by AcsTool` on affected frames.
- MVP: values contained in a single segment (the normal case — headers fit in the first segment). If a header line spans
  segments, the MVP masks from the header name to the end of that segment and the beginning of the next until CRLF using the
  per-stream segment order from `TcpStreamTracker`; PT2 switches to the reassembler's offset map.
- Checkbox **"Include credentials (unmasked)"** (default off), with a warning; the choice is not persisted.
- Masking never applies to the live view (the user is on their own PC; the Headers tab already masks in the UI — packet hex
  shows raw bytes, labelled).

### 12.3 Open in Wireshark

- `IExternalToolLauncher.OpenInWireshark(path)` (new abstraction in Presentation; WPF impl in App):
  1. `PacketCaptureSettings.WiresharkPath` if set; else 2. `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\App Paths\Wireshark.exe`;
  else 3. `%ProgramFiles%\Wireshark\Wireshark.exe`; else 4. shell-open the `.pcapng` (file association); else banner "Wireshark not
  found — file saved to … [Open folder]".
- "Export & open" = export current scope to a temp-named file in the exports folder, then launch. Also an **Open folder** button.

## 15. How this complements (not duplicates) `HttpMessageCapture`

| Question | App layer (existing) | Wire layer (Packet Trace) |
|---|---|---|
| What did the CPE/ACS send (plaintext, also for HTTPS)? | ✔ `HttpMessageCapture` body + headers, parsed summary | Plaintext HTTP only; HTTPS shows TLS records |
| Did the SYN reach the PC? Did the ACS answer the SYN? | ✗ (only "connect failed/timeout" class) | ✔ |
| Who closed the connection, FIN or RST, when? | ✗ (only an exception class) | ✔ |
| Retransmissions, zero window, MTU/fragmentation, ICMP unreachable | ✗ | ✔ |
| Exact bytes on the wire incl. header order and chunking | Partly (Kestrel header order, de-chunked body; IMPLEMENTATION_NOTES) | ✔ |
| Session/RPC semantics, outcomes, notes | ✔ | Borrowed via correlation; PT2 re-parses wire bodies with the same `ICwmpParser`/`IMessageSummarizer` |
| Storage | `InMemorySessionStore`, `CaptureBudgetBytes` | `PacketStore`, own `FrameBudgetBytes`; never writes to `ISessionSink` |

The only new data the app layer records for this feature is `ExchangeEndpoints` — the join key between the two worlds.
